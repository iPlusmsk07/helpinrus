# План безопасного внедрения

Этот план не даёт автоматического разрешения на изменение production. Каждый этап завершается проверкой результата.

## Этап 1. Сохранить результат аудита

1. Сохранить локальную ветку и итоговый ZIP с контрольной суммой.
2. Не удалять tag `baseline-pre-implementation-2026-08-24`.
3. Не добавлять в Git пароли, access tokens, recovery codes и дампы базы.

Критерий готовности: архив открывается, контрольная сумма совпадает, production не менялся.

## Этап 2. Создать Draft Pull Request

Статус: завершён 28 августа 2026 года. Draft PR создан, проверки GitHub зелёные, merge не выполнялся.

1. Отправить только ветку `audit/security-reliability-2026-08-27`.
2. Создать Draft PR в `main`.
3. Убедиться, что GitHub Actions завершился успешно.
4. Проверить список файлов: не должно быть дампов, `.env`, паролей и лишних архивов.

Критерий готовности: PR остаётся Draft, проверки зелёные, merge не выполнен.

## Этап 3. Проверить Netlify Deploy Preview

Статус: завершён 28 августа 2026 года. Preview собран из ветки аудита, защищён входом Netlify, интерфейс и заголовки проверены, внутренние файлы возвращают 404.

1. Открыть созданный preview URL.
2. Проверить главную страницу, каталог, профиль гостя, мобильную ширину и установку PWA.
3. В Network/Headers убедиться, что присутствуют CSP, DENY, `nosniff`, Referrer-Policy и Permissions-Policy.
4. Проверить, что `/supabase-schema.sql`, `/package.json` и `/README_УСТАНОВКА.txt` возвращают 404.
5. Не регистрироваться и не выполнять операции записи в production Supabase.

Критерий готовности: интерфейс работает, заголовки активны, технические файлы недоступны, production URL не изменился.

## Этап 4. Создать отдельную тестовую базу

Статус: завершён 28 августа 2026 года. Миграции применены только к временному проекту. Повторяемый сценарий `scripts/verify-supabase-rls.mjs` выполнил 35 позитивных и негативных проверок с тремя аккаунтами. Во время первого прогона обнаружена и исправлена блокировка удаления аккаунта связанными чатами; повторный прогон и очистка завершились успешно.

1. Создать новый тестовый проект Supabase без реальных пользователей и данных.
2. Выполнить по порядку `supabase-schema.sql`, `supabase-auth-migration.sql`, `supabase-security-hardening.sql`.
3. Создать минимум три тестовых аккаунта: заказчик, помощник и посторонний пользователь.
4. Проверить запреты: нельзя назначить себе `admin`/`verified`, изменить чужой профиль, читать чужую переписку или создать разговор без принятого отклика.
5. Проверить разрешения: владелец меняет имя/город, создаёт своё задание; помощник откликается; участники читают свою переписку.
6. Убедиться, что удаление каждого тестового аккаунта очищает связанные данные без ошибки внешнего ключа.

Критерий готовности: все негативные и позитивные сценарии подтверждены, SQL-протокол сохранён без секретов.

## Этап 5. Подготовить живую базу

1. Сделать новый зашифрованный backup и проверить его восстановимость на тестовой базе.
2. Запланировать короткое окно обслуживания.
3. Проверить существующие строки на ограничения до валидации constraints.
4. Применить hardening одной транзакцией.
5. Сразу выполнить read-only и авторизованные smoke tests.

Критерий готовности: резервная копия проверена, политики работают, ошибок в приложении нет. При ошибке транзакция откатывается.

## Этап 6. Финальное решение о merge

1. Снять Draft только после этапов 3–5.
2. Повторно проверить diff, Actions, Deploy Preview и базу.
3. Получить отдельное явное подтверждение владельца.
4. Выполнить обычный merge без force push.
5. Проверить новый production deploy и записать commit SHA и deploy ID.

## План отката

- Код: вернуться к tag `baseline-pre-implementation-2026-08-24` или повторно опубликовать Netlify deploy `6a73c0754a28d8000804190f` только по отдельному решению.
- База: при ошибке во время скрипта сработает rollback транзакции. После commit восстановление выполняется только из проверенного backup по отдельному плану.
- Никогда не откатывать базу «поверх» новых пользовательских данных без анализа потерь.
