# Действия при утечке, сбое или потере данных

## Главное правило

Сначала остановить распространение проблемы и сохранить доказательства, затем восстанавливать работу. Не удалять логи, commits, deploys и файлы до фиксации времени и обстоятельств инцидента.

## Если раскрыт пароль или токен

1. Записать время обнаружения, сервис и тип секрета, не копируя само значение в отчёт.
2. Немедленно отозвать токен или сменить пароль в соответствующем сервисе.
3. Завершить неизвестные активные сессии.
4. Проверить журналы входов, Actions, Netlify deploys и Supabase logs за период возможной утечки.
5. Если секрет был в Git, считать его скомпрометированным даже после удаления файла.
6. Проверить, где этот секрет использовался, и обновить только необходимые защищённые хранилища.
7. Не отправлять новый секрет в чат и не делать его снимок.

## Если раскрыт `service_role` Supabase

1. Остановить публикации и серверные процессы, которые используют ключ.
2. Заменить ключ в Supabase.
3. Обновить только серверные environment variables.
4. Проверить Auth, Database, Storage и API logs на массовое чтение или изменение.
5. Проверить пользователей, политики RLS и важные строки базы.
6. Публичный frontend никогда не должен получать новый `service_role` key.

## Если сайт перестал работать после deploy

1. Зафиксировать новый commit SHA, deploy ID, время и симптомы.
2. Не менять базу одновременно с диагностикой frontend.
3. Проверить Netlify deploy log и заголовки ответа.
4. Если ошибка только в коде, по отдельному решению повторно опубликовать последний рабочий deploy.
5. Базовая точка: commit `f89c0fe7d0f940edbecbb36232d4bb5c78f9a728`, deploy `6a73c0754a28d8000804190f`.
6. После отката выполнить read-only smoke test и записать результат.

## Если ошибка возникла при SQL hardening

- До `commit`: транзакция должна быть отменена командой rollback или автоматически при ошибке.
- После `commit`: не выполнять обратные SQL-команды наугад.
- Сравнить схему, policies и grants с тестовым проектом.
- Восстановление backup выполнять сначала в новом тестовом проекте.
- Production restore требует отдельного плана потерь данных и подтверждения владельца.

## Регулярный backup

1. Создать логический dump схемы и данных проверенным инструментом Supabase/PostgreSQL.
2. Не сохранять пароль в команде, истории терминала или имени файла.
3. Сразу поместить dump в AES-256 зашифрованный контейнер.
4. Удалить незашифрованный временный dump после проверки контейнера.
5. Рассчитать SHA-256 и хранить её отдельно от файла.
6. Держать минимум две копии в независимых местах.
7. Ежеквартально выполнять пробное восстановление в отдельный проект.

## Минимальная запись об инциденте

- дата и время с часовым поясом;
- кто обнаружил;
- затронутый сервис;
- что наблюдалось;
- какие действия выполнены;
- какие ключи заменены без указания значений;
- какие данные могли быть затронуты;
- результат проверки и восстановления;
- меры, исключающие повторение.
