# Действия при утечке, сбое или потере данных

## Главное правило

Сначала остановить распространение проблемы и сохранить доказательства, затем восстанавливать работу. Не удалять логи, commits, deploys и файлы до фиксации времени и обстоятельств инцидента.

## Если раскрыт пароль или токен

1. Записать время обнаружения, сервис и тип секрета, не копируя само значение в отчёт.
2. Немедленно отозвать токен или сменить пароль в соответствующем сервисе.
3. Завершить неизвестные активные сессии.
4. Проверить журналы входов, GitHub Actions, production deploy, Nginx и
   `helpinrus-auth` за период возможной утечки.
5. Если секрет был в Git, считать его скомпрометированным даже после удаления файла.
6. Проверить, где этот секрет использовался, и обновить только необходимые защищённые хранилища.
7. Не отправлять новый секрет в чат и не делать его снимок.

## Если раскрыт `APP_SECRET` или SMTP-пароль

1. Остановить публикации и сервис `helpinrus-auth`.
2. Сменить раскрытый секрет; SMTP-пароль дополнительно отозвать у почтового
   провайдера.
3. Обновить только `/etc/helpinrus/auth.env`, не копируя значение в Git или чат.
4. При смене `APP_SECRET` завершить все активные сессии и отозвать одноразовые
   ссылки восстановления.
5. Перезапустить сервис, проверить локальный health endpoint и журналы без
   вывода секретов.

## Если сайт перестал работать после deploy

1. Зафиксировать новый commit SHA, каталог релиза, время и симптомы.
2. Не менять базу одновременно с диагностикой frontend.
3. Проверить GitHub Actions, `journalctl`, журнал deploy и заголовки ответа Nginx.
4. Если ошибка только в коде, по отдельному решению атомарно вернуть ссылку `/var/www/helpinrus` на последний рабочий релиз.
5. Базовая точка: commit `f89c0fe7d0f940edbecbb36232d4bb5c78f9a728`.
6. После отката выполнить read-only smoke test и записать результат.

## Если ошибка возникла при изменении схемы SQLite

- До `commit`: транзакция должна быть отменена командой rollback или
  автоматически при ошибке.
- После `commit`: не выполнять обратные SQL-команды наугад.
- Сравнить схему с новой временной базой той же версии приложения.
- Восстановление backup сначала проверить на отдельной копии файла.
- Production restore требует отдельного плана потерь данных и подтверждения
  владельца.

## Регулярный backup

1. Создать согласованный snapshot через SQLite online backup API; при обычном
   копировании предварительно остановить `helpinrus-auth`.
2. Сохранить вместе основной файл и необходимые `-wal`/`-shm` данные либо
   выполнить checkpoint до резервирования.
3. Сразу поместить backup в AES-256 зашифрованный контейнер.
4. Удалить незашифрованную временную копию после проверки контейнера.
5. Рассчитать SHA-256 и хранить её отдельно от файла.
6. Держать минимум две копии в независимых местах.
7. Ежеквартально выполнять пробное восстановление в отдельный временный каталог.

## Минимальная запись об инциденте

- дата и время с часовым поясом;
- кто обнаружил;
- затронутый сервис;
- что наблюдалось;
- какие действия выполнены;
- какие ключи заменены без указания значений;
- какие данные могли быть затронуты;
- результат проверки и восстановления;
- меры, исключающие повторение.
