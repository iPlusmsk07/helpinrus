# Безопасный процесс разработки проекта «Помогай»

## Основной источник кода

После подтверждения базовой линии основной источник кода — ветка `main` репозитория `iPlusmsk07/helpinrus`. Новая работа всегда начинается от актуального подтверждённого состояния `main`, если для конкретной задачи письменно не зафиксировано другое основание.

## Обязательные правила

1. Одна задача выполняется в одной отдельной ветке.
2. Прямые изменения в `main` и production запрещены.
3. Каждая задача проходит через Pull Request.
4. До commit и до merge проверяется полный diff и список изменённых файлов.
5. Перед merge обязательны локальная production-сборка и предусмотренные задачей тесты.
6. Merge запрещён, пока тесты не завершены успешно и владелец явно не подтвердил результат.
7. Секреты, пароли, токены, `APP_SECRET`, SMTP-учётные данные и значения закрытых переменных окружения запрещено добавлять в код, документы, commit и Pull Request.
8. Force push, переписывание истории и удаление веток, tags, commits или deploys запрещены без отдельной задачи и явного подтверждения владельца.

## Именование веток

Формат: `<тип>/<краткое-название-в-kebab-case>`.

Допустимые типы:

- `feat/` — новая функция;
- `fix/` — исправление ошибки;
- `chore/` — техническая работа;
- `docs/` — документация.

Пример: `chore/safe-development-baseline`.

## Постановка задачи Codex

Каждое задание должно содержать одну цель, точное имя ветки, разрешённые и запрещённые файлы, критерии готовности и проверки. Codex должен показать полный diff и перечень изменённых файлов. В задании отдельно указываются запреты на секреты, merge и production deploy.

## Порядок разработки и проверки

1. Зафиксировать задачу, разрешённые файлы и критерии готовности.
2. Создать ветку от подтверждённого основания.
3. Изменить только разрешённые файлы.
4. Проверить полный diff и список файлов.
5. Проверить отсутствие секретов и случайных изменений.
6. Выполнить тесты, соответствующие риску задачи.
7. Создать Pull Request в `main`, оставив его Draft до завершения проверки.
8. Проверить собранный каталог `www` локально и убедиться, что внутренние файлы в него не попали.
9. После успешных тестов получить явное подтверждение владельца на merge.
10. После merge проверить production и записать новый commit SHA и deploy ID.

## Проверка production-сборки до merge

Сборка проверяется локально без обращения к production-базе:

- выполнить `pnpm test` и `pnpm build`;
- открыть локальную сборку `www`;
- убедиться, что HTML, CSS и JavaScript загружаются;
- проверить отсутствие новых ошибок сборки и загрузки;
- убедиться, что SQL, README, package metadata и секреты не попали в `www`;
- повторно убедиться, что production URL и production commit не изменились.

До merge запрещено направлять тестовые операции записи в production-базу. Для интеграционных сценариев используется отдельный тестовый контур.

## Порядок слияния

1. Убедиться, что Pull Request больше не Draft только после завершения всех проверок.
2. Повторно проверить diff, тесты и production-сборку.
3. Получить явное подтверждение владельца.
4. Выполнить merge без force и без переписывания истории.
5. Запустить повторяемый deploy на `201.51.4.212` и дождаться его успешного завершения.
6. Зафиксировать production commit SHA и каталог релиза после публикации.

## Rollback dry run

Реальный откат в рамках фиксации базовой линии не выполняется.

Точка восстановления:

- baseline tag: `baseline-pre-implementation-2026-08-24`;
- baseline commit: `f89c0fe7d0f940edbecbb36232d4bb5c78f9a728`.

Порядок действий при отдельно подтверждённом откате:

1. Остановить новые изменения и записать текущие production commit SHA и путь активного релиза.
2. Проверить `/var/www/helpinrus/.deployed-commit` и список неизменяемых релизов в `/var/www/helpinrus-releases`.
3. Убедиться, что выбранный предыдущий релиз связан с нужным commit и содержит непустой `index.html`.
4. Не переключать симлинк `/var/www/helpinrus` без отдельного явного подтверждения владельца.
5. После подтверждённого атомарного отката открыть `https://201.51.4.212` и выполнить read-only smoke test.
6. Проверить systemd-сервисы, Nginx, production commit SHA, загрузку HTML/CSS/JS и отсутствие новых ошибок.
7. Записать результат отката в отдельный отчёт.

Baseline tag не перемещается и не перезаписывается. Восстановление кода через tag и переключение production-релиза — отдельные действия, каждое из которых требует отдельного плана и подтверждения.
